# rag-eval

一个 RAG 检索层的**可复现评测**：9 篇真实工程文档、94 个检索块、22 条用例，纯标准库实现，跑一次不到 1 秒。

不是 benchmark，是「我怎么知道自己做的 RAG 到底行不行」这一件事的最小闭环。

---

## 这是什么

一套针对私有文档问答系统的评测脚手架，包含三部分：

| 部分 | 内容 |
|---|---|
| **语料** | 9 篇真实的工程运维文档（来自我自建的 jarvis-hub 项目 `docs/`，已脱敏），按标题切成 94 个检索块 |
| **用例** | 22 条，分三组：召回 12 条、跨文档综合 5 条、**拒答 5 条**（语料里根本没有的问题） |
| **脚本** | `run_eval.py`：手写 BM25 + 中文 bigram 分词 + 阈值扫描，**零第三方依赖** |

## 这不是什么

说清楚边界，比吹成绩重要：

- **不是公开 benchmark**。22 条用例是我为自己的文档写的，样本小，不能用来横向比较不同 RAG 产品。
- **不是生产系统的复刻**。生产环境用的是 BM25 + pgvector 向量检索的混合方案；本仓库只实现了 **BM25 单路基线**，用来量化「纯词面检索能做到什么程度」。
- **没有端到端评测**。端到端（答案准确率）需要调 LLM，涉及 API 成本，本仓库不预置结果。

---

## 怎么跑

需要 Python 3.8+，无任何依赖：

```bash
python run_eval.py               # 完整评测
python run_eval.py --sweep       # 扫拒答阈值，看「召回 vs 拒答」权衡
python run_eval.py --calibrate   # 打每条用例的 top-1 分数，看分布
python run_eval.py --topk 5      # 改检索深度
```

结果写入 `results/latest.json`。

## 结果

```
语料    9 篇 → 94 个检索块
用例    22 条（召回 17 / 拒答 5）
参数    k1=1.5  b=0.75  top_k=3  拒答阈值=6.0
──────────────────────────────────────────────
hit@3          13/17 =  76.5%
拒答准确率       5/5 = 100.0%
综合准确率       18/22 =  81.8%
检索延迟 p50     0.1 ms
```

### 为什么要扫阈值

拒答的判据是「检索最高分低于阈值」。这个阈值不能拍脑袋定 —— 因为**正例和拒答的分数是重叠的**：

```
正例 top1：min=3.77  median=8.38  max=17.24
拒答 top1：min=2.85  median=3.99  max=5.78
重叠区间：3.77 ~ 5.78   ← 单一阈值切不开
```

扫出来的权衡（节选，完整见 `--sweep`）：

| 阈值 | hit@3 | 拒答 | 综合 |
|---|---|---|---|
| 3.00 | 82.4% | 40.0% | 72.7% |
| **4.00** | **82.4%** | **60.0%** | **77.3%** |
| 5.50 | 76.5% | 80.0% | 77.3% |
| **6.00** | **76.5%** | **100.0%** | **81.8%** ← 默认 |
| 7.00 | 64.7% | 100.0% | 72.7% |
| 8.00 | 58.8% | 100.0% | 68.2% |

**这个表就是结论**：阈值越高，拒答越准，但真问题被误拒的也越多。取综合准确率最高的 6.00 作默认值 —— 因为对 RAG 来说，**编造答案是致命的，拒答是可接受的**。

## 三条失败用例，以及它们说明了什么

比通过率更有信息量的是失败：

| 用例 | 期望 | 实得 | 原因 |
|---|---|---|---|
| 「本月 API **花了多少钱**，怎么查？」 | COST.md | DEPLOY.md (3.77) | 文档写的是「账单」「费用查询」，问句是口语化的「花了多少钱」，**bigram 完全不重叠** |
| 「中枢**记住了**哪些关于我的事，怎么删除？」 | OPERATIONS.md | JOB-SEARCH.md (4.94) | 「记忆」vs「记住」，「岗位采集」文档里有大量「数据/记录」干扰词 |
| 「API 费用**超预算**了怎么办？」 | COST.md | PLAN.md (5.85) | 「预算」在 PLAN.md 里也出现过，但那里讲的是项目规划不是成本控制 |

**三条失败指向同一个根因：BM25 只看词面，不懂语义。**

这恰好解释了为什么生产系统最终要用 **BM25 + 向量检索的混合方案**：词面匹配解决不了「花了多少钱 = 费用查询」这类同义表述。

## 局限性

诚实列出来，因为面试官会问：

1. **样本太小**。22 条用例、94 个检索块，置信区间很宽。任何一条用例翻转都会让指标变动 ±4.5%。
2. **中文分词是 bigram**，不是真正的分词。对「花了多少钱」这类口语化表达召回很弱 —— 这既是局限，也是本次评测的真实发现。
3. **纯 BM25 单路**。生产环境是 BM25 + 向量混合检索；本仓库的 76.5% 只代表**词面单路**能做到什么程度，不能代表生产效果 —— 生产那套没有在同等用例上测过，所以这里不给对比数字。
4. **延迟 0.1 ms 只代表内存 BM25**（94 个块、22 条查询取 p50）。生产检索还要叠加向量召回、网络往返和生成，不可直接比较。
5. **没有端到端评测**。检索命中 ≠ 答案正确。要评价「回答对不对」，必须接 LLM 判分，本仓库没做。

```
rag-eval/
├── corpus/            9 篇工程文档（来自 jarvis-hub/docs，已脱敏）

```

### 用例格式

```jsonl
{"id":"r01","group":"recall","q":"怎么新增一个 YAML 声明式工具？","expect_docs":["TOOLS.md"]}
{"id":"n01","group":"refuse","q":"这个项目支持 Kubernetes 部署吗？","expect_docs":[]}
```

- `group=refuse` 时 `expect_docs` 为空，判据是「检索分数低于阈值」
- 其余情况下判据是「期望文档出现在 top-k 里」

## 一个自己的 bug

写阈值扫描表时发现：第一版 `summarize()` 里，真问题只判「是否命中期望文档」，**没判分数是否达到阈值**。

结果扫出来 `hit@3` 恒为 82.4% 不随阈值变化 —— 明显不合常理（阈值越高，应该越多真问题被判成「查不到」才对）。

修法是：**真问题的判定必须同时满足「命中期望文档」和「分数 ≥ 阈值」**，因为分数低于阈值时系统实际会回答「查不到」，等于漏召回。

这个 bug 说明一件事：**指标代码本身也会错，看数字前先问「这个数字合不合理」。**
